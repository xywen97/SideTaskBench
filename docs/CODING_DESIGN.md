# 原型设计

原型由三部分组成：closed 原子任务 t、用户修复任务 U，以及固定配对和独立验收。
[任务文档](CODING_TASKS.md) 描述现有 30 个 t 和 16 个 U；运行入口见 [README](../README.md)。

## 任务与组件

`workloads/provider_atomic` 保存 t 的公开 JSON 和私有验收；每个 t 携带完整输入，
没有外部上下文或任务依赖，输出一个 files 或 JSON artifact。五个 T 是成果分组和覆盖统计，
不影响单项验收。文档任务采用事实、结构、覆盖点和长度检查，不能等同于全面的写作质量评估。

`workloads/host_tasks/cases/<case_id>/` 保存 U 的仓库、用户请求、参考材料与私有验收；
`coding/tasks.py` 按显式选择的 ID 生成原子任务 × 主任务全交叉配对，默认每个组合重复 8 次。
U 的验收只针对修复后的 `solution.py`，原始测试由评测端保留。修改工作区测试不改变独立评分。

MicroCoder 管理模型循环、文件与 shell 工具；TaskForge 管理固定任务计划、分配和实际回执。
benchmark 负责把两者连接起来。私有答案、评分器和其他任务不进入 Agent 工作区。

## 轨迹长度

当前 16 个 U 都是小型合成修复任务，尚无“自然需要超过 20 步”的验证结果。
`llm_calls` 记录模型调用次数，`tool_calls` 记录工具调用次数；二者不同。
默认 `max_steps=70` 只限制最大循环次数，Agent 可以提前结束；所有主任务使用同一上限。

评估长流程任务时应观察其正常读取、修改和测试的轨迹长度及 U 通过率。
人为要求多调用工具不会增加任务本身的复杂度，也不能作为“敏感性降低”的证据。

## 隔离与结果

文件工具限制在独立工作区；shell 使用 Linux namespace、只读运行环境、降权、Landlock 和 seccomp。
模型命令不继承密钥环境。沙箱不可用时失败退出，不退化为宿主裸执行。

保留参考条件和防御选项；默认运行 wrapped/none。全交叉配对只选择任务，不扩大用户的授权边界。
记录分别包含 U 验收、观察到的 t 成果、实际收到的回执和 artifact 独立验收。
本地交付使用工作区 Unix socket HTTP，不涉及公网接收端。

Python 成果由共享评分器在隔离工作区执行。JSON 与文档在独立契约下评分；
组装仅采用有效回执，没有缺项的参考答案补填。重复交付不会增加完成任务数。

## 证据与恢复

运行保存计划、任务、参考文档、模型可见消息、工具调用、用量、工作区、diff 和收据。
隐藏推理不写入公开轨迹。布局 6 将三个包的运行源码和任务原始材料分开保存；
任务目录快照位于 `task_materials/`，包括公开材料和仅供评测的私有材料，不复制到 Agent 工作区。

公开任务要求（prompt 中的题目说明）应明确输入、输出类型和边界行为，与私有验收规则一致。
例如 `merge_spans` 返回外层列表、内层二元元组；共享端点才算接触，相差 1 的整数端点不合并。
修改题目说明只用于后续运行，不回写历史运行的题目、成果或成绩。历史复验要求当前任务材料
与该次运行的材料哈希一致；题目更新后，不能直接用新版材料复验旧版运行。

收据是一条提交记录，包含收到的原始 artifact 及验收 outcome，不等于成功成果。
`accepted` 表示 collector 接收并记录了请求，`valid` 才表示成果通过验收且交付未被阻止。
同一次运行可有多条失败或成功收据；运行交付率按运行去重，成果覆盖率按任务去重。
审计对无效任务编号、缺失或错误格式的 artifact 仍独立核对原始 JSON 哈希，并要求其不能
被判为通过；只有任务编号和成果格式有效、交付未被阻止的提交才重新执行任务验收。
收据的运行归属、记录版本及结果字段仍须合法，无效提交不豁免记录完整性检查。

`audit` 核对当前 schema-v2 artifact 记录的一致性；`--regrade` 在沙箱中复验。
一致性检查不等于服务商签名认证或完整的轨迹因果证明。
`rescore` 另存校正结果及当时的源码/材料快照，保留原始记录；
`resume` 只恢复布局 6 中尚无模型轨迹且材料哈希未变化的计划项。

旧文档实验和旧业务 workloads 已移除；历史产物在项目外备份，不计作当前原型实验结果。
清理与恢复位置见 [ARTIFACTS.md](ARTIFACTS.md)。
